# ADR-001: FitFlow High-Level Technology Architecture

## Status

Accepted

## Context

FitFlow requires:

- Android, iOS and Web support
- High performance
- Real-time features
- AI-based personalization
- Secure handling of health-related information
- Scalability
- Maintainability for a mid-sized development team

The architecture must support these requirements without introducing unnecessary complexity.

## Decision

The proposed FitFlow architecture will use:

- Flutter for the cross-platform frontend
- NestJS for the main backend APIs and real-time WebSocket services
- FastAPI for the AI and recommendation service
- PostgreSQL as the primary system database
- Redis for caching and frequently accessed data
- AWS Cognito for authentication and authorization
- AWS S3 or equivalent object storage for media and files

## Reason for the Decision

### Flutter
Flutter is selected because it allows FitFlow to support Android, iOS and Web using a largely shared codebase while maintaining strong UI performance.

### NestJS
NestJS is selected as the main backend because it provides a structured modular architecture, TypeScript support, REST APIs, dependency injection and WebSocket support.

### FastAPI
FastAPI is used as a separate AI service because Python provides strong support for AI and machine learning libraries.

### PostgreSQL
PostgreSQL is selected because FitFlow contains strongly related data such as users, workout plans, nutrition records, progress records and permissions.

### Redis
Redis is used to cache frequently accessed data and improve response times.

### AWS Cognito
AWS Cognito is selected for managed authentication, MFA, OAuth 2.0 / OpenID Connect support and strong AWS integration.

## Alternatives Considered

- React Native
- Kotlin Multiplatform
- Swift / SwiftUI
- FastAPI as the complete backend
- Go backend
- MongoDB
- Firebase
- DynamoDB
- Firebase Authentication
- Auth0
- Supabase Auth

## Positive Consequences

- High frontend code reuse
- Good cross-platform support
- Clear separation between core backend and AI logic
- Strong relational data integrity
- Scalable managed authentication
- Better maintainability
- AI service can scale independently

## Negative Consequences

- The development team must support Dart, TypeScript and Python
- Multiple services require monitoring and deployment management
- AWS Cognito configuration can be more complex than simpler authentication platforms

## Risk Mitigation

- Keep only one separate AI microservice initially
- Define clear API contracts
- Use automated tests and CI
- Centralize logs and monitoring
- Use secure environment variables and secret management
- Apply least-privilege permissions
